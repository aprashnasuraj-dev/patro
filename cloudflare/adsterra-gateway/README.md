# Adsterra gateway: source snapshot and date-page layout

This directory records the gateway that was serving the `aafnaipatro.com/date/*` and several tool routes on 5 November 2026. `patro-adsterra.mjs` is a snapshot of the pre-existing deployed module; it is not evidence of Adsterra account approval, consent compliance, or successful paid impressions. Its broad advertising CSP allowances predate this change and need separate, traffic-tested security review.

The gateway retains its `DATE` and `ORIGIN` service bindings. On a successful, uncompressed `/date/YYYY-MM-DD` HTML GET, `date-native-layout.mjs` moves the existing single native slot after the date facts and before date navigation. It does not add ad requests or change the existing Popunder or Social Bar units. Unknown templates, duplicates, partial requests, errors, non-HTML, compressed and large responses pass through unchanged. Cache policy is retained; body validators are removed when HTML changes. The `x-patro-ad-layout: date-inline-1` response header identifies a changed response.

Run `node --test date-native-layout.test.mjs` from this directory. Deployment must preserve the existing service bindings and all unrelated Worker routes and must verify the live date page and non-date pass-through. This is a gateway-specific source snapshot; the root Worker, atlas, library and separately deployed advanced tools have independent deployments. Do not deploy or replace their assets from this directory.

This placement change does not implement a consent-management platform, configure advertiser categories, or measure fill. Use the publisher dashboard and a suitable consent implementation where required before treating the overall setup as compliant. Do not count page views, script loads, tests or bot requests as paid ad impressions.

`calendar-native-layout.mjs` and `root-entry.mjs` describe a separate, guarded placement change for the existing root Worker: on known Bali and international calendar templates, it moves the same native unit immediately after the introductory hero. Unsupported markup and other paths pass through. `root-entry.mjs` is a snapshot of the live wrapper around its already-deployed `optimized-entry.js`, not a complete root build. Any root Worker version must preserve and compare its live assets, asset routing, headers, redirects, bindings, scheduled handler and compatibility settings before deployment. Do not rebuild or replace the live asset collection from this snapshot.

`library-article-layout.mjs` and `library-entry.mjs` record the production library wrapper. For eligible published `/article/` and `/blogs/` HTML, it relocates the single existing native unit just after the article headline, or after the third direct paragraph when the headline structure is absent. It leaves the R2 content unchanged. The HTMLRewriter test double exercises decisions locally; actual Worker verification is still required. Research pages and unsupported templates retain their existing behavior unless a separate second native unit is configured.

The change to `worker/optimized-entry.ts` integrates the live root wrapper's asset fallback, Adsterra decorator and calendar placement into the repository's normal Worker entry. This does not reconcile every independently deployed Worker or authorize a root asset deployment: verify live asset and route parity before any future release.

The 5 November follow-up adds preconnect hints for the existing Popunder and Social Bar/Native script hosts. On known `/tool/<slug>` pages with `#ct-tool`, a clearly labelled optional Smartlink is placed after the tool. The publisher-supplied native unit remains single per page. Long library articles also receive a labelled in-article Smartlink and, when the expected structure is present, their existing related-reading block is moved higher. Existing in-article images without explicit loading settings are deferred. No new R2 content is published.

An optional Worker variable `ADSTERRA_NATIVE_SECOND` accepts JSON with `src` and `container` from a separate, approved Native Banner snippet. When configured, it replaces the optional link after known tool containers with a genuine second native unit. The same variable enables the library's second article/research placements. Reusing the first code or configuring a malformed value is ignored. Do not assume the option has enabled a second ad until the distinct code is present in the relevant Worker binding.

The newer publisher-supplied Smartlink is used for top, inline and tool-adjacent links; the prior Smartlink is retained at the bottom. Smartlinks require a voluntary click and are not counted as native ad impressions. The same link update was applied directly to the separately deployed atlas Worker and 20 independent advanced-tool Workers; their production entrypoints must be reconciled before any future independent deployment.

When both the native and Social Bar script requests fail, a dismissible notice asks visitors to consider allowing ads. It does not bypass blockers, send tracking, make additional ad requests, force clicks or block content. Dismissal is stored for the current browser session. Library article/research responses also send a preload hint for their existing stylesheet.

The separate `patro-discovery-gateway` owns the exact `/robots.txt` and `/sitemap.xml` routes. It forwards to the existing root Worker using its `ORIGIN` service binding and adds references to the library article, catalogue and subject-directory sitemaps, preserving existing entries. The main site's asset routing is unchanged. The shared library Worker renders subject directories from published catalogue data, and adds direct navigation to article responses. Search discovery and ad fill remain subject to search-engine and ad-network decisions.

On supported `/tool/*` and browser-tool category pages, the root wrapper and ad gateway add crawlable links to the library subject and catalogue directories, including pages whose main tool renders in the browser or whose asset bypasses the root Worker. Twenty-two matched tools also link to up to three relevant published articles. Unsupported paths and non-HTML responses pass through.

The separately deployed advanced-tool Workers can use `advanced-tool-entry.mjs` with their exact previously deployed module as `original.mjs`. The captured original modules and their checksums are stored in `cloudflare/advanced-tool-workers/`. The entry adds the directory links through `advanced-tool-discovery.mjs` and provides direct article links for a small set of matching tools. Do not replace an independent Worker's module, bindings, handlers or runtime with a generic build; compare the current active version and retain the original source when preparing any update.

`ad-diagnostics.mjs` starts downloads of the three existing executable Adsterra scripts early using matching preload hints, while keeping the original asynchronous script tags and one placement per unit. On explicitly public HTML it also preserves existing Link headers and adds preconnect hints for the ad hosts, enabling Cloudflare to emit 103 Early Hints where supported. Cloudflare caches hints by URI, ignoring query strings, and can emit them before a later response; do not use these headers on private or personalized pages. In-article, after-tool and bottom Smartlinks remain labelled and have larger mobile touch targets. It also records ad script `loaded` or `error` status, a native slot visible for one second, trusted Smartlink clicks and native-link interactions in the existing GA4 property. It honors explicit analytics denials and the advanced tools' opt-in controls. It does not invoke ad links or add any request to a first-party telemetry Worker. A script load, visible slot or observed interaction is not proof of an Adsterra-paid impression or click; cross-origin frame clicks are not observable. Check the real active Cloudflare version and preserve all bindings, handlers and static-asset configuration before uploading a future version.

For a long article with exactly one known reading rail, `library-article-layout.mjs` inserts a clearly labelled Smartlink into that rail without changing R2 article objects. The library stylesheet already makes the rail sticky on desktop and static on smaller screens. This is an additional voluntary link, not an additional Native Banner or ad impression. Library version `e26a9818-3e97-4d07-91e2-4c4203624331` is live; other Workers may still run the earlier shared diagnostic-module version until independently updated.

The shared ad decorator also places one labelled Smartlink immediately after the known `.mm530-frame-wrap` tool container across recognized calculator, converter, generator and other MM530 routes. If a distinct approved `ADSTERRA_NATIVE_SECOND` unit is configured, that unit occupies the after-tool placement instead. The existing 550 `/tool/` pages continue to use their `#ct-tool` mount. Neither placement requires changing the generated tool pages, an extra Worker invocation, or a synthetic click. Gateway version `41fbe0e1-5230-4c5c-8d17-89825ef7fc86` and root version `d0e92456-a5cf-4cfe-8cd1-1fb6ca2ce263` were active on 6 November 2026; compare current deployment and assets before any later update.

On recognized article layouts, the library wrapper now positions the existing top Smartlink immediately after the first native unit rather than before the headline. Only a single unambiguous managed link is moved, and no new ad request or R2 object is added. The change is live on library version `9809bef8-451f-4659-8479-e736399ba149`; previous version `e26a9818-3e97-4d07-91e2-4c4203624331` is available for rollback. Two article templates were checked through a 0% version override, which verifies markup placement but not paid impressions.

The final Advanced Tools postbuild also preserves the three library sitemap references when a new root asset bundle is built. `node scripts/indexnow-changed-content.mjs` previews a batch from live public sitemaps using the project's existing key; append `--submit` only when notifying IndexNow about real changes. It validates the published key, excludes other hosts and query strings, limits the batch to 10,000 URLs, and reports rate limits without automatic retries. A one-off request for 3,802 URLs on 6 November 2026 Nepal time returned HTTP 429; it was not accepted.
