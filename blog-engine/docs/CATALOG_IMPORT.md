# Catalog intake — actual cloned source data, not decoration

Three pinned Git submodules now live in `missionmangal/vendor/`. Clone with `git clone --recurse-submodules` or `git submodule update --init --recursive`. `python -m engine.catalog_import --output blog-engine/data/api_candidates.json` reads **mnfst's machine-readable data.json** and **the two other repositories' README.md files**, extracts catalog entries, records provenance and de-duplicates website domains. Every result is `candidate_unverified` and `enabled: false`. The inventory becomes a discovery input to the editor/provider-review workflow; **it cannot secretly activate hundreds of endpoint calls**.

The importer must not execute any upstream code or assume a homepage equals an API endpoint. The lists overlap heavily and some advertise temporary signup credits, non-commercial trials, expired promotions, affiliate links, proxies with unclear terms or models that may not exist. Commercial publishing requires independent official-doc verification for endpoint, model, credentials, quotas, training/privacy, pricing, image/video rights and output license. Only approved records graduate to `missionmangal/config/adapter-allowlist.json`, after review. Existing six user-reported GitHub secret names can be mapped within approved manual workflows, not exposed in a PR. Every actual service call uses the quota-aware fallback router, not random catalog endpoints.

The directory imports run offline in CI from the submodule checkout and can be refreshed only by an upstream SHA-update PR; never silently track latest main. RapidAPI and public-apis, already recorded separately, need equally vetted data-source adapters for evidence gathering. A listing in any directory is not a valid article citation.
