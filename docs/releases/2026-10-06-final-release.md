## Why the last smoke failure was not a production outage

The previous production smoke test received successful `200` responses from the live site for both archive pages and sync APIs. The failure was caused by an overly strict backend-header assertion in `scripts/cloudflare/smoke-r2-release.mjs`.

Observed successful examples included:

- historical `/date/1826-04-11` served by `cloudflare-r2-public-archive`;
- historical `/api/v1/sync?date=1826-04-11` served by `cloudflare-r2-calendar`;
- current `/date/2026-10-06` served by `cloudflare-r2-public-archive`;
- current `/api/v1/sync?date=2026-10-06` returned `200` through `cloudflare-native-indexed-calendar`.

The smoke script previously required every sync response to report `cloudflare-r2-calendar`. Commit `54c0c5ef96027db3d37b1e556ec2d33720b9789a` narrows the fix to test expectations: deep archive checks remain strict on R2, while current-day sync is allowed to use the valid indexed-calendar path. Production routing behavior was not weakened or changed by that fix.

- No mass alias/cross-product page generation should be added merely to inflate page count.

## Storage and quota release policy

Production public-reference reads follow the repository's quota-preservation design:

- immutable calendar/history/reference facts prefer static/R2-backed sources;
- Cache API/KV are used for hot/reference response caching where appropriate;
- R2 stores durable public archives and reference snapshots;
- D1 remains for existing mutable/runtime contracts and must not become an avoidable fallback for immutable public archive traffic.

The calendar fast path deliberately fails closed if required immutable archive data is unavailable rather than silently converting public archive traffic into D1 read load.

## Rollback / recovery rule

If a post-deploy production regression is confirmed, rollback should restore the last known-good Worker/build artifact or revert the smallest release commit responsible for the regression. Do not modify historical source data, archive manifests, D1 schema, R2 datasets or canonical URLs as a first-response rollback unless the incident is directly proven to originate there.

The latest smoke fix is isolated to release-test expectations, so it should not be used as justification for changing working current-day or R2 runtime routing.
